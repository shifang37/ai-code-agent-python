# 评测报告

三套量化评测，脚本在 `evals/`。所有数字都是实测结果，复现命令附在各节末尾。

模型：DeepSeek（`deepseek-chat` 用于意图路由，`deepseek-reasoner` 用于代码生成），
测量时间 2026-08-28。

## 1. 意图路由准确率

需求描述进来后要先判断该用哪种形态生成（`html` / `multi_file` / `vue_project`），
判错会让后续整条流程都跑偏 —— 比如把需要路由和组件化的应用生成成单页 HTML。

数据集是 60 条人工标注的中文需求，三类各 20 条，重复 3 轮。

| | 结果 |
|---|---|
| 均值 | **98.3%** |
| 区间 | 98.3–98.3 |

三轮结果完全一致（每轮 59/60），错分集中在同一条样本上
（`multi_file` 被判成 `vue_project`），说明分类边界稳定、没有随机抖动。

复现：`python -m evals.routing_eval 3`

### 实现中踩到的坑

DeepSeek 不支持 OpenAI 的 `json_schema` 响应格式，会直接返回
`400 This response_format type is unavailable now`。而路由服务对异常是
**fail-open 回落 HTML** 的，于是症状表现为「所有需求都被判成 HTML 模式」——
准确率掉到 33%，却没有任何报错冒到调用方。

修复：所有结构化输出统一走 `with_structured_output(schema, method="function_calling")`
（`app/llm/services.py`）。这条约束已写进代码注释，避免后人改回默认值。

## 2. 故障注入自修复

度量自修复闭环的能力下界：在一个已知可构建的基线 Vue 项目上注入**确定性**的编译期故障，
然后驱动修复子图，看能否恢复、用了几轮。

跑的是 cold 臂 —— 修复时不带任何生成过程的对话记忆，模型只能依据编译器报错和
读到的文件内容定位问题，因此测出的是能力下界。

**有效性门禁**：注入后必须先跑一次探针构建并**确认构建失败**，样本才计入分母。
这道门禁不能省：像纯类型错误会被 esbuild 直接剥离，构建照样成功，
这种样本混进来会让「恢复率」被一堆本来就没坏的项目灌水。

| | 结果 |
|---|---|
| 恢复率 | **20/20 = 100%** |
| 平均修复轮次 | 1.00（最多 1 轮） |
| 无效样本 | 0 |

分类别：

| 类别 | 结果 |
|---|---|
| T1 模板语法 | 4/4 |
| T2 脚本语法 | 3/3 |
| T3 样式语法 | 2/2 |
| I1 本地模块缺失 | 5/5 |
| I2 命名导出缺失（跨文件） | 2/2 |
| I3 依赖缺失 | 4/4 |

单例耗时 6–19 秒（复用共享 `node_modules`、跳过 `npm install`）。

复现：`python -m evals.fault_injection_eval`

**样本量说明**：20 例是单轮跑满全部故障规格的结果。它证明的是
「闭环在全部 6 类故障上都能工作」，而不是「恢复率精确等于 100%」——
要给出可靠的区间估计需要重复多轮累积到几百例。

**修复真实性抽查**：光看「构建成功」不足以说明模型真在修 —— 也可能是产物被还原了。
抽查 T1a（删掉 `App.vue` 的闭合 div）：修复后与注入前的文件做 diff，模型并非还原原文，
而是写出了自己的版本（把 `router-view` 包进 `<main class="app-main">` 并补了配套样式规则），
`dist/` 正常产出。确认是模型经 `writeFile` 工具真实修复，不是任何形式的缓存或回滚。

## 3. 构建端到端

从零跑完整工作流直到 `npm run build` 成功，度量的是「首轮直通率」与「最终成功率」。
与故障注入不同，这里的失败是**自然发生**的，不是注入的。

- **standard 组**：10 条典型 CRUD 型需求
- **complex 组**：5 条刻意挑选的高复杂度需求（多级嵌套路由、SKU 矩阵、数据大屏等），
  更容易首轮构建失败，用来真正压到自修复回路

| | 构建成功 | 首轮直通 |
|---|---|---|
| standard | **10/10** | 10/10 |
| complex | **5/5** | 3/5（其余 2 例各经 1 轮修复） |

单例耗时：standard 108–237 秒，complex 337–463 秒（含真实 `npm install` + 完整生成 + 构建）。
逐个核对产物：15 个项目全部产出 `dist/index.html` 与打包 JS，源码 9–18 个文件。

两轮都跑在加固后的构建路径上（`npm install --ignore-scripts` + 子进程环境变量白名单），
因此也顺带确认了这些安全收敛没有破坏正常构建。

### complex 组触发的两次自修复

| 例 | 首轮构建报错 | 结果 |
|---|---|---|
| #2 可视化表单设计器 | `SyntaxError: Invalid end tag.`（模板语法） | 1 轮修复后构建成功 |
| #3 多语言电商后台 | `RollupError: "t" is not exported by "src/utils/i18n.js", imported by "src/pages/Login.vue"`（**跨文件**命名导出缺失） | 1 轮修复后构建成功 |

第 #3 例值得单独说：它是**跨文件**根因 —— 报错指向 `Login.vue`，真正要改的却是
`i18n.js`。这正好考验修复提示词里「从报错中解析出相关源文件并附上内容」那段逻辑。
核对修复结果：`i18n.js` 里确实补上了 `export function t(key, params)`，
与 `Login.vue` 的 `import { t }` 对上，项目正常打包。

这类跨文件故障在故障注入评测里对应 I2 类，是六类中最难的一档 ——
而这一例是在真实生成流程中自然出现、并被自动修好的。

复现：`python -m evals.build_selfheal_eval standard`（或 `complex` / `all`）

## 4. 图片素材收集

这一路曾经**完全不工作**，而且一直伪装成网络问题。前后查出四个缺陷，
共同特征都是「不抛错，功能默默不干活」：

1. **收集计划返回 `None` 未判空**。`with_structured_output` 在模型不调用工具、
   直接回文本时返回 None 而非抛错；节点里 `None.contentImageTasks` 抛的
   AttributeError 又被节点自身的宽异常捕获吞掉，最终只表现为「收集到 0 张图」。
   三处结构化输出调用现已全部显式处理 None（`app/llm/services.py`）。
2. **undraw 接口的构建哈希已过期**。早期实现把 Next.js buildId 硬编码在 URL 里
   （`mMWmJSt23qpgo8cLTD_pB`），官方发版后变成 `9SMsYpCjXCftNdh3cu_8Q`，请求恒 404。
   现改为运行时从搜索页抓取 buildId 并缓存，遇 404 刷新一次重试，可自愈于后续发版。
3. **一条填错的子任务废掉整个计划**。模型给 `diagramTasks` 填的是
   `{"query": "收入支出统计流程图"}`，而 schema 要求 `mermaidCode`；子任务字段是必填时，
   pydantic 会让**整个计划**校验失败，内容图、插画、Logo 全部一起丢。
   现在子任务字段全部可选，由 `valid_*` 属性逐条过滤，坏任务只影响它自己。
4. **httpx 不做 Happy Eyeballs 回退**。图床的 DNS 常把 IPv6 排在前面，而不少网络环境
   到它们的 IPv6 不通，httpx 直接抛 ConnectError 也不去试后面的 IPv4
   （curl 会做双栈竞速，所以用 curl 测同一地址一直正常 —— 这正是它被长期误判成
   「本机访问不到外网」的原因）。表现是「时灵时不灵」，随 DNS 顺序漂移。
   现在连接失败会用绑定 IPv4 的传输重试一次。

另外 undraw 的搜索只对短词有效（`coffee` 有 12 条，`coffee culture illustration`
是 0 条），而规划模型产出的是描述性长短语（对 Pexels 正合适）。已加单词级降级重试。

修复后实测（记账本需求，即当初触发计划校验失败的那条）：**0 张 → 82 张**
（48 张 Pexels 内容图 + 34 张 undraw 插画）。
Logo 一路需要 `pip install '.[media]'` 装 dashscope，未装时按预期跳过。

回归测试见 `tests/test_structured_output_fallbacks.py`。

## 5. 未覆盖项

如实记录没测到的部分：

- **带记忆的修复对照**（先完整生成、再注入故障，用来对照「生成过程的对话记忆」
  能带来多少增益）脚本未实现。cold 臂已足以度量能力下界，这一项只影响上界的刻画。
- **Mermaid 架构图**需要本机安装 `mmdc` 且配置 COS 才能跑通，未验证。
- **故障注入只在单个基线项目上做**。故障规格里的锚点（要删哪个闭合标签、
  改哪条 import）是针对该项目手工校准的，换项目需要重新校准或改用自适应锚点。
